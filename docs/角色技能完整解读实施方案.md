## 1. 目标不变，起点已经改变

最终要回答：**某个角色的每条技能描述，究竟增加多少攻击、减少多少伤害、提供多少固定防御，以及持续多久、对谁生效、需要什么条件。** 一条描述效果对应一行答案，保留原文、原值、来源和换算依据。

采用“一次交代总目标，分批交付可读结果”。不要求用户每补一个规则都说继续，也不承诺靠一条提示词就把全部未知机制变成已确认。主持负责不跑偏，实施负责真正产出，审查负责发现会让答案出错的问题。

### 对参考资料的具体取舍

1. 初步分析报告的“36 条一致”只说明其核对范围内吻合，不等于我们本轮重新确认，也不能扩大规则范围。
2. 报告所列 3 条可升级规则应引用本项目已有证据，不以对方统计结果作为确认依据。
3. type99 的 param8／param9 是重点防错样本：当前本项目证据把 param9 对应到受伤量相关增量，param8 的移动速度解释有单样本限定。不要笼统写成“防御 +30%”，更不能互换参数。
4. 343 条候选按实际引用角色数和补齐价值排序；decisive 高只是值匹配线索，无法证明因果、单位、对象或条件。报告中的 11 条高风险推断单独保留，不能因命中多而优先确认。
5. 不复用已知错误：按 denju_to 查传授的做法、将地形编号当百分比、把所有值为 1 的字段跳过、把不同类型的回复超上限位直接通用化。
6. 对方统计未覆盖所有类别；Leader、Class、PASSIVE、CrossWorld、英雄技、Extra、传授等仍须从本项目结构发现。不能用对方 1610 行作为“全部技能字段”的分母。

## 2. 完成什么才算有用

默认范围：现有名册中可玩卡牌版本，加上经核对需补入的可玩条目；NPC／敌人另列。先沿用 2236 作为候选数，再输出与参考项目 2233 的具体 ID 差异及分类理由，不强求两边数量相同。存在争议的卡单列，不因此阻止其余角色继续处理。

相同 cid 的来源选择复用已经验证的规则：缓存整条记录优先，缺记录时才按相同命名空间回退 APK；保留来源，不拼成不存在的混合记录。同名不同 cid 不合卡。子技能引用的回退要逐种来源确认，不从角色合并规则自动推导。

每条答案包含：角色 cid／名称、技能类别／ID、原文片段、中文效果、原始参数、数值或公式、单位和基数、对象／必要条件／时间次数、来源定位、证据状态、未解决点。已有结构能表达就复用，不为统一命名重建框架。

示例（仅示意格式，不是实际游戏结论）：

| 描述 | 可读答案 | 原值与依据 | 状态 |
|---|---|---|---|
| 攻击力提升 | 攻击 +50%，自身，条件满足时 | 原值 1.5；已证实此类型使用 (x−1)×100 | 已确认 |
| 防御力提升 | 目前只确认与接受者攻击值有关，尚缺基数说明 | 原值 0.3；不能直接写成减伤 30% | 部分解释 |

区分“代码确认”“原文直接给数”“推断”“未知”；原文数字已知不意味着触发机制也确认。倍率、增加比例、减伤、固定防御、百分点分别处理。缺失、null、零不能互相替代。

**一张卡完整**：实际技能组全部描述已登记；每条有足够回答用户问题的数值／公式或文字机制说明；无影响答案的关键缺口。无需恢复最终扣血、实际解锁状态或完整战斗引擎。条件公式可以是完整答案，但未知基数不能藏在字母变量里。

每批只报：目标卡数、完整卡数、部分卡数、尚缺关联卡数；另附新增解释效果数和主要缺口。按互斥状态统计角色。描述尚未拆全时明确“描述分母未闭合”，不能用成功行数冒充全量覆盖。

## 3. 新的阶段安排

这里的 P1—P4 是本版技能解读阶段，与历史解包 A—E 无关。

| 阶段 | 做什么 | 交付什么 | 何时进入下一步 |
|---|---|---|---|
| P1 范围与首批答案 | 复用名册，列差异，关联技能组，应用已有规则，做通用角色输出 | 角色范围、首批可读档案、缺口与候选队列 | 用户能打开角色看具体答案；做 R1 后扩大批量 |
| P2 按缺口补规则 | 用参考候选缩短找方向的时间，用本项目记录／代码确认含义 | 每批更新规则、受影响角色、覆盖增量 | 可连续多批；无关难点不拖住其他角色 |
| P3 全范围整理 | 对目标卡全部生成档案，处理遗漏类别和引用，输出未知原因 | 全范围 JSON／CSV／可读页、进度与缺口 | 生成齐全即可进行 R2；语义未知仍必须保留 |
| P4 交付接入 | 把新脚本、规则、说明纳入既有可复现和分层交付方式 | 运行说明、依赖与结果清单；按用户要求准备发行包 | 必要隔离样本通过，最终说明与实际范围一致 |

### P1：先做出能看的结果，不再只做字段字典

- 查看当前任务记录，复用已完成部分。先做 2236／2233 的 ID 差异，避免重新建名册或猜差异原因。
- 建立角色到实际技能类别、根记录和子效果的关联；保留断链。普通 skilllist、heroicskilllist、Boss 表不能只凭同号 ID 合并。
- 首批复用 cid30236，另选能覆盖 APK 独有、缓存覆盖和不同技能结构的少量角色。样本由结构决定，不机械规定数量。
- 将已有规则直接转成角色答案，未知项也显示。没有现成通用查询时做最小入口：cid／名称查询、JSON／CSV、简单 HTML；先不建设复杂网站。
- 将参考候选接到真实缺口上：每个候选显示能影响哪些角色、哪些描述。优先队列不按参考表顺序照抄。
- 首次通用结果做 R1。只阻止存在错误的关联／换算进入批量；无关的候选研究可以继续。

### P2：一个批次真正补齐一组答案

默认顺序：用户指定角色 → 高频攻防核心数值 → 即将完整的角色所缺规则 → 其他实际描述。候选 type8、1059、18、67、1029 等只作为起查方向，是否先做取决于真实覆盖，不提前宣布它们已确认。

每批选一组共享逻辑的缺口，通常 1—3 个类型足够：

1. 看原始记录和描述，比较参考分析，提出可检验的具体解释。
2. 只追踪会改变数值、基数、对象、条件的相关代码。已有证据够用就复用；必要时做最小原生片段验证。
3. 明确规则适用的来源、类型和字段，保存证据位置，再批量应用到受影响角色。
4. 用能够区分错误解释的样本核对，例如字段相等时再找不相等样本，确认不把速度当防御。
5. 更新角色答案和缺口，给出实际新增成果，继续下一批。

研究没有新证据时留下“缺哪段代码／哪份记录，补到后如何判断”，换一项推进；不要为某个低覆盖难点无限延长对话。现有候选耗尽不代表全部角色已解释，应回到角色缺口找下一步。

### P3：查漏的是描述，不是所有二进制字段

- 覆盖目标集合全部卡牌，包括无法完整解释的卡；每张卡展示已知答案与缺口。
- 核对原始描述是否有片段未入表，尤其对方未覆盖的类别、值为 1、flag／iParam、传授及复合技能。
- 翻译只改变表述，不增添原文没有的数值。文本与代码冲突时并列记录，不让网页文案覆盖原值。
- 更新覆盖清单，做 R2。仍有关键未知就称“阶段成果”，保留后续队列；只有声明范围内全部满足标准才称“完整解读”。

### P4：接上既有交付，不重新做一个发布项目

- 自有脚本、必要规则与简短文档按现有 Git 规范管理；数据和成果进入 B 包，大媒体继续走 C 范围，不强行入 Git。
- 正式生成入口接受输入／输出路径；使用的规则和证据索引须随包提供或有明确生成办法。不依赖他人参考目录才能运行。
- 区分“从规则重新生成角色答案”和“重新执行历史逆向研究”：前者应有可运行命令，后者声明真实依赖与已验证范围。
- 对本次新增的技能生成链做一次独立目录小样本运行，检查输入、规则、模板是否齐全，确认结果与正式样本一致。无改动的解包链沿用已有证据。
- 与 R2 合并检查交付说明即可；不另设第三轮大审查。后续若实际制作发行包，再遵循 AGENTS 的包清单与压缩包核对要求，不重做语义研究。
- 本方案不授权提交、推送、Release 上传或公开发布；沿用当前暂缓发布决策，需执行时按用户具体授权处理。

当前已有文件足够开展 P1—P4，默认在电脑完成。只有明确找到影响目标答案的缺失资源且现有 APK／缓存无法提供，才说明具体需补采什么并请求手机操作。没有实机证据就不写“已实机验证”。

## 4. 审查只看会影响答案的事情

| 时点 | 必须看什么 | 不做什么 |
|---|---|---|
| R1：首批通用档案之后 | 角色范围差异有记录；来源和技能关联正确；原文→字段→数值能追溯；type99 等错配未引入；未知未隐藏 | 不重新审完整解包，不要求全部字段已解释，不逐张人工看全量角色 |
| P2 风险触发 | 新规则改变公共换算、推广到新命名空间、出现来源冲突时，独立核对相关证据和受影响样本 | 不为每加一个普通规则单开审查；仅增加记录数量不触发全套回归 |
| R2：P3／P4 收口 | 全目标集都有状态；描述缺口真实可见；抽查不同技能结构和高风险规则；交付范围与依赖真实，新增生成链可复现 | 不要求所有平台安装测试，不全量重算媒体，不追查与用户数值答案无关的战斗细节 |

每条问题写：具体角色／技能／字段、证据文件位置、会让哪一句答案错、最小修改建议。按“会给错答案／会漏答案或无法使用／文字小问题”区分影响。结论用“通过”“带明确限制通过”“需修正”并说明受影响范围，不拿无关小问题阻止全部推进。

审查默认只读，报告单独保存。实施者修复，复验只查修复点及必要受影响样本。审查者必须打开关键证据，不能把初步分析报告改写一遍当作独立审查。

## 5. 三类对话怎样分工

| 对话 | 用人话说负责什么 | 写入范围 | 什么时候换新对话 |
|---|---|---|---|
| 主持 | 看有没有离目标更近；决定下一批；把任务和交接说清楚 | 只维护自己的进度文件，默认 `docs/tasks/character-skills-progress.md` | 反复丢失当前任务、重复安排已完成工作时，凭进度文件接手 |
| 实施 | 写代码、找证据、生成真正能看的答案、修审查指出的问题 | 自己的任务记录、约定脚本和输出；默认新模块 `scripts/character_skills/`、结果 `output/character_skills/` | 一组成果稳定交付后可切；开始重复读相同资料、混淆来源或方向失控时及时交接 |
| 审查 | 独立检查答案有没有错、有没有漏、说明是否夸大 | 仅 `output/character_skills/review/<review_id>/` 和必要独立复跑目录 | R1、R2 建议各开新对话；同一次审查的修复复验留原审查对话即可 |

默认一个实施者持续写，主持和审查不同时改公共脚本。根 HANDOFF／STATUS 由明确的整合者维护；未指定且有并行任务时只写自身交接。任务记录不是文件锁，但不能占用别人进行中的写入范围。

**对话数量不用堆：一个主持＋一个实施，到了审查点再开审查。** 主持不必每批批准才能执行；正常批次由实施连续推进，只在范围改变、真实冲突或关键缺证时报告。新对话读取文件化交接，不复制整段历史聊天。慢本身不能证明上下文过长，还要看是否在长时间运行工具、重复探索或输出无关内容。

模型名称按用户所用平台选择；此处 Kimi 3 对应官方 Kimi K3。模型用途参考了官方介绍，分工判断由本方案给出： [GLM 5.3 Flash 模型卡](https://huggingface.co/zai-org/GLM-5.3-Flash)、[DeepSeek 4.1 Flash 公告](https://api-docs.deepseek.com/news/news260910/)、[Kimi K3 公告](https://forum.moonshot.ai/t/kimi-k3-is-here-our-most-capable-model/480)。核阅日期：2026-10-17。

## 7. 主持对话提示词（完整复制）

```text
你负责本项目角色技能解读的进度和方向。我的目标是：查一个角色，就能知道每条技能描述增加多少攻击、减少多少伤害、提供多少固定防御，以及必要的对象、条件和持续时间。
```
