## 1. 目标与执行顺序

目标是提高“单位时间内新增的、玩家能用的答案”，同时使已验证规则能处理同类新记录，而不需要不断新增具体卡号名单。

依次实施三层，不把第三层当作前两层的前置条件：

1. **立即调整节奏**：研究与正式发布分开；最多将同一周期内三个成熟语义批次合并为一个交付包，一次正式全库重建。各批来源、收益和独审范围仍分别可核。
2. **优先改小而确定的能力**：建立一个真实规则族的结构化推广试点；账本改为在一次运行内按卡读取复用，验证结果等价。
3. **有计时证据后再做真正增量生成**：依赖追踪、按影响卡失效、混合复用后的签名及账本一致性必须先验证。未通过前仍采用“合并后一次全库重建”。

不以恢复整个战斗引擎、全库重译、统一CLI、历史存储治理或更换所有模型作为提速前置。原有Y.G.优先、来源分层、保护卡、HOLD18、新原生及跨层专项的授权边界保持；新发现的边界冲突只影响相应候选，不拖住可独立交付部分。

## 2. 同类字段怎样批量推广

### 2.1 分清三个问题，分别出结果

| 层次 | 回答什么 | 推广方法 |
|---|---|---|
| 字段规则 | 数字代表什么、怎样换算、单位是什么 | 复用已确认的表/类型/字段规则，在已证适用域内遍历全部记录 |
| 来源与条件 | 该记录属于哪个角色、技能、档位、对象、条件 | 根据真实引用链与结构选择记录，处理多候选和缺失 |
| 描述归属 | 这项效果对应哪句话、哪个子句 | 根据效果类型、句型、对象和阶段绑定；歧义保留未知 |

字段公式已确认而描述未绑定时，可以展示“已证参数，描述归属待核”，但不能提前计入描述已答。允许一条描述同时交付已解单项和未知单项。

### 2.2 规则族的最小定义

优先复用现有 `rules.py`、`profiles/rules.json` 与推断模块；不另造独立规则引擎。每个拟推广族至少明确以下内容，可放在现有规则声明和函数中，避免维护两套同义注册表：

| 内容 | 必须说明 |
|---|---|
| 身份 | 输入版本/命名空间、表、效果类型、字段路径；不能只看param名字 |
| 适用域 | 已证来源层、类型、版本或结构限制；单记录证据不能自动升级成全类型证据 |
| 换算 | 原值→数值/单位/基准；缺失、null、零、异常值分别处理 |
| 来源结构 | 从角色到父记录、子记录的真实引用路径、预期槽位结构 |
| 选择与归属 | 唯一候选如何判断；对象、条件、阶段和描述如何对应 |
| 拒绝原因 | 同号跨层、多候选异值、对象冲突、未知阶段等须有明确原因 |
| 证据 | 原始记录定位、公式证据、归属证据；确认/类型外推/推断保持分离 |

已知公式在已证域内应接受不同数值，不把旧卡的原值写成语义准入条件。当前输入哈希/原值核对可继续用于防输入漂移，不能与“只有这个数值才懂”混为一谈。

### 2.3 执行流程

1. **先列候选**：对声明输入范围扫描同一规则族，输出全部命中记录及其角色/描述引用，不只收集预先知道的卡号。扫描可包括非Y.G.候选，但Y.G.优先审查和交付，非Y.G.只在同一已证域内连带。
2. **按原因分流**：分成可自动出值并绑定、仅能出字段值、需要补证、范围外四类。每个候选有状态与原因；已处理、未处理和失败均能对账。
3. **验证结构规律**：至少覆盖原有正例、原名单外真实正例（若存在）、不同原值、相关真实反例以及缺失/null/零等适用边界。预期来自原表与独立规则证据，不调用被测函数生成预期。
4. **修改消费者**：让实际生产入口消费同一规则。检查是否缺来源参数、只走旧视图、答案未被账本消费；不能只增加规则登记而没有生产效果。
5. **先生成候选差异**：用小范围候选输出列清新增/变化/保留未知，不覆盖正式目录。对候选逐项做机器化来源解引用、公式重算与单位/对象检查；独审按不同语义分支和风险抽核原始证据，不机械人工逐卡重审同一公式。
6. **一族一次收口**：批量接入同一已证结构；例外留下具体原因，不能每新增几个卡号就重新开一次正式批次。

正式交付可以保留“本轮授权的目标集合”用于差异控制，但该集合只限定此次发布范围；它不是语义判断的唯一依据。输入版本改变时重新扫描、核适用域，不承诺任意新版本自动兼容。

### 2.4 首个推广试点

优先评估 **G1镜像绑定中来源唯一、结构一致的子族**。当前G1直接按row_id、pattern、子记录和原值名单放行，是明确的改进对象，但不能先假定全部25行能用一条规则概括。

- 目标：结构规则选出真正属于当前传授/当前档位的记录，复用已知伤害公式；不按卡号或数值大小猜归属。
- 必留反例：同文不同档位、链外较高值、对象/阶段不符、APK与CACHE同号、空值与真零。
- 7251等同值但记录不唯一的情况单列：继续披露原有限制，未经来源语义核实不得升级为唯一来源已确认。
- 当前同卡基础答案可作交叉检查，不能成为语义正确的唯一证明；两处同时错误仍可能同值。
- 若扫描没有新的安全可推广项：如实报告零新增，不凭空扩大域；仍可交付经验证的结构能力，但不计成新数值收益。
- 若G1不存在可独立收口的子族，主持用实际候选表选择已有公式且引用唯一的族；登记替换理由，不无限停在选题研究。

G7多段增益作为后续族，先解决阶段、对象和竞争记录的结构判定；不因0.6与0.7都会换算而直接给升级句出数。若消费G7行级bindings汇总，先修已登记的1/4槽汇总问题；未消费则不把它扩大成全线前置。

## 3. 小批次怎样合并，正式生成放在哪里

### 3.1 三种单位不得混淆

- **研究子项**：一个公式、引用分支、模板或反例的研究/实现单位，可多项并行。
- **实质语义批次**：按共同规则族与风险划分，分别留收益及独立语义审查结论。它仍是“每三批一次方向复核”的计数单位。
- **交付包**：一次冻结的源码/输入集合及正式生成，可包含同一周期内1—3个成熟语义批次。机器工作共享，但批次不合并成一个收益数字。

小子项应在开工前按规则族归入同一语义批次；不事后重命名已经计数的批次，不为少审查把无关机制塞进一批。一个包不得跨越第三批后的停审边界。工程提速和纯登记维护按既有约定不计实质解析批次。

### 3.2 推荐流水线

```text
按族扫描并分配研究子项
        ↓
各子项局部实现、样本生成、正反例检查
        ↓
各语义批次独立核验规则与候选结果
        ↓
主持合并成熟批次，做共同路径交互检查，冻结一个版本
        ↓
一次正式全库重建 → 一次账本 → 一次入口/选题链
        ↓
一次固定全套机器检查 + 各批最终语义核对 + 合并差异核对
        ↓
统一收官；周期满三批则方向复核并按约定停下
```

冻结前语义核验通过只写“候选审查通过，待正式交付”；正式产物核对后才能写最终通过。可以由同一独审上下文连续核多个同族批次，但审查者仍须独立于实施，结论逐批可定位。

### 3.3 主持的合并与止等规则

- 优先合并同公式/同模块/同验证风险且都已成熟的子项，最多包含当前周期剩余的三个语义批次。
- 有未解决来源歧义、新原生需求或跨层风险的子项，从本交付包移出并保留待办，不把已成熟项等住。
- 不以凑满三批作为交付前提。建议试行“成熟项等待合并不超过一次主持工作时段、最多2小时”；这是调度上限建议，不是研究完成时长承诺。用户要求立即查看结果时优先交付成熟部分。
- 正式生成前，把输入版本、源码、规则、受影响卡集、预期变化类别、审查覆盖和容量检查固定下来；冻结期间不再往生产代码追加其他候选。
- 并行人员修改不同推断模块；公共消费者、账本、索引、依赖声明由主持指定唯一整合者。未成熟代码放任务候选目录，不让它因 `card_page*.py` 扫描进入本包源码签名。
- 候选目录只隔离必要代码/配置和少量结果；APK、缓存及大表只读引用。不得通过换输出目录绕过已有容量与保留规则。
- 隔离运行要核实全部实际读写路径，尤其是仍使用全局正式路径的消费者。现有检查器没有局部入口时，先做必要的最小路径适配或采用独立定向核对；不能仅传一个输出参数就宣称完全隔离，也不能把局部检查写成全套通过。
- 对多批共同触达的行/字段记录归属；同一效果不能在两个批次重复认领。无法拆分的共同修正单列“联合影响”。

### 3.4 当前工具限制与禁止的捷径

现有生成器按整套代码/依赖签名判断复用。仅加 `--resume` 不能解决改了源码后的全库失效；`--cid` 子集目前用于调试，不能把子集生成说成已完成全库一致交付。

第一阶段仍保留正式全库生成，只减少正式生成次数。不得改写旧receipt、伪造统一签名、更新latest掩盖混合版本，或取消来源/哈希检查。实现真正增量前，无法证明局部等价的正式变化按当前完整生成方式发布。

## 4. 必须保留与可以合并的检查

| 检查/工作 | 局部研究阶段 | 正式交付包阶段 | 合并规则 |
|---|---|---|---|
| 原值、单位、计算基准、对象/条件/档位 | 每个改变语义的分支必查 | 核正式结果保持候选结论 | 同一公式证明复用，不同边界单独核 |
| 来源解引用、原表/命名空间/输入版本 | 候选出数时即检查，尽早发现漏来源字段 | 全部变化答案机器核对 | 同一工具复用，不再为每小项写一套校验器 |
| 原错误、相邻反例、合法正例 | 每个实质修复覆盖相关风险 | 合并代码后复跑受影响用例 | 同根因用例合并，不能删关键反例 |
| 独立语义审查 | 候选规则和绑定定向审查 | 对送审版本核对最终结果 | 同一上下文可接续，逐批保留结论 |
| 旧正确答案、范围外与保护卡 | 用基线和预计影响范围约束 | 全包差异核对，非授权变化为阻断 | 共享一份真实包前基线，避免多份全量复制 |
| 页面、账本、入口、选题版本一致 | 局部检查，不把候选写成正式 | 每交付包一次全链路 | 冻结版本未变就不按每子项重跑 |
| verify_full、账本自检、A7 | 按改动调用相关检查；无法局部调用不伪称全套通过 | 完整跑一次，当前分别17/9/29项，以执行时实际版本为准 | 审查可核回执并独立重算风险点，不强制每方机械重复全套 |
| 隔离复现 | 小样本证明代码与来源闭合 | 覆盖受影响语义分支和保护样本；首次推广扩大到必要目标集合 | 固定版本的同一复现证据可复用，不重复建整库副本 |
| 玩家中文说明、未知披露 | 新增效果写清对谁/多少/条件/时长 | 抽查本包数值、条件、部分解析样本 | 不把全站重译/排版升级加成每批前置 |
| 容量、备份、回滚与输入保护 | 独立输出纳入既定范围 | 正式生成前准入检查 | 同一包做一次有效处置；不提高限额/自动删除 |
| 进度、收益、任务交接 | 子项状态轻量更新 | 一次终态统计与同步 | 进度页是唯一当前看板，报告引用它和版本化数据 |
| 第三方方向复核 | 仍按现行触发条件 | 满三个实质批次或出现重要共同风险时进行 | 不因合并交付包而取消或推迟越界 |

必须保持独立的还有：不同输入版本/来源层的语义证明、不同阶段/对象的冲突判断、已有保护项、不同授权边界。语义审查不能被“机器全绿”替代。

同一问题继续按现行“初审一次、集中修复后定向复核最多一次”的规则处理。非阻断项登记后继续；真实阻断不能因到轮次上限而写PASS。新证据或新修改只触发受影响检查，已验证且版本未变的部分不重开研究。

## 5. 代码改动的分阶段任务书

以下是给主线主持的实施划分，本方案起草阶段不执行。

| 顺序 | 任务 | 优先修改位置 | 验收与交付 |
|---|---|---|---|
| 0 | 落实新节奏与接手入口 | 现行实施方案、进度页、HANDOFF、本轮任务卡 | 新旧条款无冲突；明确首个交付包、批次计数、唯一整合者 |
| 1 | 同族候选扫描与G1结构推广试点 | 既有推断模块；必要时在 `scripts/character_skills/` 增一个共用扫描/判定辅助模块 | 候选全集有处置；新值无需新增卡号代码；合法/非法例可区分；新增收益与能力收益分开 |
| 2 | 账本按卡读取复用 | `scripts/character_skills/effect_ledger.py` 的逐描述读卡段 | 与冻结旧实现同输入输出等价；读取次数按卡而非按描述；记录实际时间/内存，不能只宣称优化 |
| 3 | 试行一次合并交付包 | 复用现有正式驱动与验证入口 | 成熟小项统一生成一次；各批独审/收益仍独立，整包机器检查通过 |
| 4 | 对照成本决定是否增量化 | 批生成、依赖声明、写入/复用协议、账本接口 | 先给依赖失效方案；候选增量结果与同版本全量结果一致后才投入正式 |

任务1、2仅在写入范围分离、共同接口明确时并行；共享文件由单人整合。任务2若延误，不阻塞已成熟的任务1交付。优先用既有模型和授权分工，不为提速另开一轮模型选型工程。

### 账本读卡优化的验收要点

用同一冻结输入对旧/新实现各跑一次受控比较；只允许显式声明的运行时间等非语义字段不同，所有描述、效果、答案引用、状态、待办和计数必须一致。可以按卡建立临时索引并在处理后释放，避免把节省读盘变成不可接受的内存增长。缓存仅限一次冻结运行，不跨输入/代码版本长期复用。

不得为优化跳过独立读源核验；可以把“每行重读同卡”改成“每卡独立重读一次并核该卡所有行”，保持核验语义。

### 真正增量生成的后续门槛

只有计时表明值得投入时才启动。至少设计并验证：

- 按卡输入与规则依赖能覆盖所有消费者；共享规则/绑定/拆句器/账本变化能正确扩大失效集合。
- 无法确定影响范围时自动退回全量，不静默复用。
- 单卡改动、共享规则改动、仅展示变化、原始表变化各有代表性失效检查。
- 复用卡和新生成卡共同组成可解释的一致版本；未重算卡的复用理由可追溯，不能给旧结果伪盖新签名。
- 中断、重跑、恢复时不发布半成品；合并后账本/索引/选题链与全量计算一致。

此阶段是后续选择，不因本方案要求一次实现所有能力。

## 6. 收益、耗时与停止深挖

每交付包只维护一份机器生成的收益明细。至少分列：

1. 新确认的公式/语义；单纯新增规则登记键不计新公式。
2. 首次得到解释的原始参数槽：按输入版本、来源层、表、记录、字段去重，不按不同数字值去重。
3. 既有值新增描述绑定，以及旧未解效果真正转已答的数量。
4. 完整描述增量、仍未解部分、受益角色与Y.G.分项。不得将受益卡数称为整卡完成数。

另记录实际阶段时间：研究/实现、候选检查、独审、正式生成、账本、固定检查、返修、等待。无法独立计时就写未知，并行时长不直接相加；不得用文件修改时间估算工时。

试行评价看：每包正式全库生成次数、因来源/元数据漏项造成的生成后返修次数、同族新增记录是否还需手加row_id、每个阶段实测耗时，以及实际Y.G.收益。正常目标是**每包一次正式全库生成、零未解释的数值漂移**；失败返修允许重建，但须写具体原因，不用次数目标掩盖错误。

没有新证据不反复跑检查。查清目标字段的数值/单位/对象/条件后即可出该单项答案；只有下一层逻辑会改变这些要素时才继续追踪。运行时选档未证可以保留限定，不把最终扣血/完整帧模拟作为所有单项前置。

## 7. 必须让“更换主持”不丢进度

### 7.1 主线主持采用方案时必须完成的三处落地

1. **现行实施方案**：局部更新 `docs/角色技能完整解读实施方案.md` 的工作流、分级检查、周期/批次与计时条款，写清生效日期和试行范围。不能保留“每小批完整重建”与本文同时有效的冲突说法，也不能把三批方向复核改没。
2. **唯一进度页**：在 `docs/tasks/character-skills-progress.md` 顶部写当前交付包、所属语义批次、状态、最新已验收版本与下一步，并链接本轮任务卡。历史段保留；统计从正式产物引用，不手工维护第二套看板。
3. **根交接入口**：在 `HANDOFF.md` 仅加新流程入口、当前包任务卡及最近安全检查点。详细记录仍在任务目录，根文件保持简短。

每处写入前重读当前内容，只做局部合并，不覆盖其他对话新增内容。更新这三处属于主线主持实施时的职责；本独立方案没有提前改写它们。

### 7.2 每个交付包的最小交接材料

复用现有任务卡和run_record，不再新增多层管理系统。每包一张 `docs/tasks/<日期>-<包名>.md`；机器状态可在包目录的现有run_record中扩展，确有必要才新增一个manifest。

任务卡顶部必须能回答：

| 字段 | 要求 |
|---|---|
| 授权与边界 | 用户本次目标、允许改动范围、保护项、暂停/继续条件；写清计划中但未授权专项 |
| 当前状态 | 研究中/候选已审/版本已冻结/生成中/待终审/已验收，区分各子项 |
| 负责人与在途任务 | 主持/实施/独审、实际模型档位、可用任务ID、各自写入范围；不依赖记忆 |
| 已验收基线 | 输入版本、campaign/snapshot、规则指纹、可恢复的必要代码/配置位置 |
| 候选版本 | 源码/规则实际哈希、修改文件清单、候选目录；不能只写Git HEAD，未提交变化也须可恢复 |
| 已完成证据 | 检查命令、返回码、回执、独审结论及其准确适用版本 |
| 待办与疑点 | 阻断/非阻断、候选排除原因、未完成的具体步骤；不笼统写“继续推进” |
| 下一步 | 下一条可执行命令或明确人工判断、运行目录、输入输出、成功标准 |
| 回退/恢复 | 最近已验收入口、生成是否完整、已写产物与在途预约；不包含未经授权删除动作 |

新增命令只有实现并验证后才能写成“可直接运行”；方案中的未来接口不得冒充已交付CLI。大输入以路径/版本/必要哈希引用；修改源码和规则保存必要的小型版本快照或补丁及其可用基线，不复制整个游戏目录。

### 7.3 何时写检查点、何时建议换主持

以下时点立即更新本包任务卡和回执：候选准备完、独审结论返回、源码冻结、正式生成完成、终验完成，以及出现失败/中断/用户改变范围时。不能等全部成功才补写交接。

出现以下情形应先落盘交接，再建议在安全检查点换主持：上下文接近容量限制；主持反复重新查找同一入口/遗忘边界；换班或用户要求；会话/代理不可恢复异常。不得为了“坚持做到最后”拖到上下文失效。

若正在生成/审查，交接必须记录在途任务ID、冻结版本与写入位置，新主持先确认它仍在运行还是已经结束；不重复派单、不启动第二个同目录写入者。未确认状态不能据文件较旧强行接管。无需让在途任务因换主持重做已完成工作。

### 7.4 新主持接手操作

1. 读AGENTS、HANDOFF当前入口、现行方案改动段、进度顶部、本包任务卡；不通读全部历史。
2. 查Git状态及活动任务写入范围，核候选/正式版本与交接哈希；恢复真实文件状态，不能仅信上次聊天说“已完成”。
3. 核对在途任务与生成回执：已完成则收结果；运行中则接续观察；中断则从最后有效检查点恢复。
4. 旧证据与当前输入/源码/规则一致时直接复用；只有版本改变或新疑点才重跑受影响检查。换主持不是重做研究或全量重建的理由。
5. 在进度顶部写明接手人、当前包状态和下一动作，沿已有授权继续。模型实际不可用时按现行约定说明，不暗中更换或伪称核验。

### 7.5 交接也要验收

首个试行交付包冻结时，做一次轻量“仅靠文件接手”核对，可由现有独审者完成，不另建长期审查链：不看原聊天，也能找到最新已验收基线、当前候选、已通过检查、唯一写入者和下一动作。若做不到，先补缺的入口/状态；不要求换人重跑整套生产流程来证明可交接。
