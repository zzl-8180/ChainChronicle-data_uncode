## 2. 数据链已核实

当前正式链路：

```text
已解包主表 + 技能关联/规则/绑定证据
  → scripts/character_skills/card_page_data.py
  → pages/<cid>/card.json
  → card_page_render.py → pages/<cid>/index.html

card.json + campaign + profiles/rules.json
  → effect_ledger.py → effect_ledger/{ledger.jsonl,metrics.json,backlog.json}

card.json 的角色基础信息 + campaign 汇总
  → card_page_index.py → pages/{index.html,all_cards.html}
```

`card_page_data.py` 读取当前规则元数据并通过既有规则消费者生成答案。正式首页只携带 CID、名称、称号、头像可用性等目录数据，没有消费效果账本来生成逐角色状态。正式详情页虽有部分效果未解提示，首页仍不能回答“哪些角色已解到什么程度”。旧 `query_effect_dictionary.py` 也不是当前答案的统一查询入口。

样稿链路是 `_research/extract_facts.py` 抽取正式数据后写入 `_data/facts_<cid>.json`，再由 `build_variant_b.py` 读取这些副本及 `_research/copy_<cid>.json` 生成页面；重跑 B 版渲染器本身不会先刷新正式数据，也不会自动更新逐条中文文案。

| CID | 样稿描述行 → 当前 | 样稿答案项 → 当前 | 源文件 SHA 是否相同 |
|---|---:|---:|---|
| 350 | 65 → 65 | 50 → 64 | 否 |
| 30239 | 57 → 57 | 52 → 57 | 否 |
| 30337 | 62 → 62 | 47 → 67 | 否 |
| 合计 | 184 → 184 | 149 → 188 | 三卡均已变化 |

这是各行 answers 数量对照，不是 39 项独立新效果的认定。已足以证明样稿不能当作最新主线展示。

## 3. 现在到底解出了多少

本轮逐行读取 `effect_ledger/ledger.jsonl`，按 CID、record_type、ledger_row_status、status 聚合，与 metrics.json 对账一致。

| 逐角色状态 | 数量 | 含义 |
|---|---:|---|
| 至少有一项已挂接的效果答案 | 1,422 | 包含推断／局部公式；不能标成“整卡已确认” |
| 其中全部描述完整 | 4 | CID 29、2020、5023、7050；按当前账本规则判断，不等于全部机制已实机验证 |
| 有答案但尚未全部完整 | 1,418 | 上两行之差 |
| 暂无已挂接的效果答案 | 814 | 不表示没有原始数据、原文数字或字段解释；只是效果账本没有 has_answer 项 |

| 描述状态（四类互斥） | 全库 | Y.G. |
|---|---:|---:|
| 完整 | 6,516 | 1,459 |
| 部分 | 264 | 57 |
| 未解析 | 8,692 | 1,008 |
| 拆分待核查 | 26,193 | 3,281 |
| 合计 | 41,665 | 5,805 |

已识别效果有答案 21,098、未解决 48,567、有依据不适用 299，共 69,964。这个分母只包含已识别效果，不能据此宣称全游戏完成率。待办 74,760 是 48,567 个效果缺口加 26,193 条拆分待核查描述，也不是角色数。

完整度与可信度是两条轴。“完整”允许包含推断答案；“拆分待核查”也可能已有多个答案。不能把全部拆分待核查都画成“完全没研究”，不能把 A 类或“存在数字”当作完成。

样例：350 有答案效果 42、未解决 65，描述完整 13／未解析 13／拆分待核查 39；30236 有答案效果 48、未解决 40，描述完整 5／部分 1／未解析 9／拆分待核查 43。两套计数分别数效果和描述，不混用。

## 4. 排版和中文表达的问题

本轮查看了旧正式页、协作者页、B 样稿的既有 350 技能段截图，并核查当前 HTML 和生成代码。

- 正式页：日文正文和 `floor/clamp(float32(...))`、pattern ID、词表／审查说明占据阅读层。用户需要先理解研究术语才能找数值。首页虽有汇总数字，却没有中文搜索、解析状态筛选或每卡进度。
- B 样稿：已有中文、分档、来源折叠和颜色标签，但每条描述被包成多层卡片，大标题／空白／说明占用过多高度。历史截图中一个主要效果便占据大半屏；还存在“本样稿没有已审定数值”等以研究过程为中心的正文。核心数值与效果句仍分离，“更多能力”折叠不利于快速扫清全卡状态。
- 协作者新版：中文姓名与称号、头像目录、职业／所属／武器／星级筛选、回退恢复、紧凑角色资料、按技能分段、数值紧贴中文句子，能直接服务找卡和读技能。这些应成为重做骨架，不只是参考配色。
- 协作者也有不能照搬的部分：正文数字统一金色；来源主要靠鼠标悬停；斜杠档位容易分不清条件；不同来源数值混在流畅中文中。其 10 月 27 日文档明确记载部分页面写法简化了算法（例如人数阶梯乘算写成加算），不能移植为我方事实。中文译名、术语和数值应分别管理来源。

## 5. 建议的重做范围

1. **角色目录**：头像、中文／日文名、职业／所属；默认清楚显示“已有答案、尚未解决、需核对描述”，支持全部／Y.G.／有答案／暂无答案／全部描述完整及职业、所属筛选。返回目录恢复查询与位置。数据范围保留我方 2,236 卡，不随参考包缩成 2,233 卡。
2. **角色详情**：紧凑头部后立即进入技能；按必杀、能力、共鸣、羁绊、传授等实际类别导航。中文效果句中紧贴数值和单位，分支写清触发条件，未知项留在同一效果旁边。日文原文和研究细节次一级呈现，不能抢占正文。
3. **状态表达**：完整度采用“已有答案／尚未解出／描述仍需核对”；可信度保留绿／橙／灰红等颜色加文字。数值规则确认但角色归属推断时，不仅用绿色“确认”概括整个效果。具体标签从现有 numeric_evidence、association_evidence、evidence_scope 映射，不能由 UI 自行升级。
4. **讲人话**：优先“攻击力提高 22.5%”“减伤比例尚未解出”“这一档伤害输入为基础值的 25 倍，实际选档待确认”。计算、float32、表名、参数位、证据路径放“计算与来源”；影响使用的条件仍在正文。不能为流畅把固定防御写成百分比减伤，或把局部输入公式写成最终伤害。
5. **接入方式**：新增只读展示适配层，以 `cid + row_id + effect_id + answer_refs` 对齐 card.json 和 ledger；直接保留来源、分支、缺失值语义。按 campaign／rules／数据版本检查一致性。中文层绑定原文校验值，源文变化时标待更新；不再养一套脱离主线的 facts 副本。
6. **接入主线交付**：主线正式产物成功后生成目录及阅读层；页面显式显示本次数据版本和更新时间，新增答案与缺口变化可查看。不让展示修改反向改变解析规则、账本定义或历史周期报告。

下一步宜先做一个可接入的真实数据原型：目录＋350／30239／30337／30236，另加 29（全部描述完整）和 1（无已挂接答案），验证长文、多档、部分有值、完全无值及完整卡。原型必须同一生成器读取当前数据，验收后才能推广全库；不继续积累孤立手写页面。
