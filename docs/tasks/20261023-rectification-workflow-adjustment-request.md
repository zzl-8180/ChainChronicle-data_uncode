## 三、主持要怎么改

### 1. 把验收目标从“几个例子通过”改成“这类错误不会再发生”

每次任务书简写四件事：本轮修什么根因、影响哪些路径、什么行为才算修对、哪些已有正确结果必须保留。

例如分类问题，不能只要求“349的三项改成G7”。应要求：当前效果的归属不能被同句无关效果抢走；局部命中和回退路径都受约束；改动无关子句不能改变当前效果分类；合法共享条件仍保留；没有依据时明确待分类。

实施前明确范围，审查可指出遗漏。与本轮根因直接相关的残留必须进入本轮结论，不能为写PASS临时缩小范围；确实独立的后续问题另行登记，不无限扩大本轮。

### 2. 把容易失败的验证前移，把正式交付准备后移

对共享判定、归属、完整性等容易反复的整改，默认顺序改为：

**小范围修复与正反例自检 → 独立审查根因及相邻分支 → 修法稳定后统一生成必要正式成果 → 独立核对最终产物 → 同步看板并交付。**

这是调整审查顺序，不是强制额外增加一整轮审查。原则上由同一独立审查上下文接续前后两段：前段查修法，后段查落地产物和新增差异。简单改动可合并一次完成。

不要每改几行就重做整套正式重建、指标同步和长篇收官说明。小范围结果不能冒充全量通过；最终该做的全量检查仍做。正式生成后若代码又有影响结果的修改，按影响范围补生成和复验，不能为了“一次重建”保留过期成果。

### 3. 固定送审版本，准确管理状态

用现有源码哈希、输入版本和产物标识固定送审对象，优先复用现有机制。其他任务可以并行，但不能覆盖正在审查的同一份输入或成果。必要时只隔离相关小文件，不复制整套大型资源。

若送审对象变化，明确变化范围及旧结论适用范围，不让审查者反复追移动目标。

状态分别写清“实施及自检完成”“修法审查通过，待最终产物验证”“最终验收通过”或“局部通过，仍有未闭合项”。不能把指定样例通过、带限制通过写成整项根因关闭。最终统一同步当前看板，保留历史报告，不批量改写历史数字。

## 四、执行要怎么改

## 五、审查要怎么改
