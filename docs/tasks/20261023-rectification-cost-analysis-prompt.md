# 给第三方的复核提示词：整改成本分析与提速方案评估

> 用法：把以下全部内容交给一个与项目无历史关联的第三方 AI 新对话。你是独立评估者：不要采信我的分析结论，到证据位置自行核实后给出判断。

## 一、背景

《锁链战记》数据解包项目（仓库 `E:\代码项目\锁链战记数据解包`）有一条"角色技能页主线"：把 2,236 张角色卡的技能描述逐条做数值解析（每条描述的攻/防/移/暴击/回复/时长/条件逐项给出数值、单位、条件、证据等级）。工作模式：主持（Kimi K3）调度 GLM 实施、DeepSeek 独立审查；质量标准要求"逐效果语义正确＋独立验证"。

用户发现：**整改轮总是非常费时间（单轮墙钟 2–5 小时）**，我（主持）应要求做了成本分析并给出提速建议。请独立复核我的分析是否属实、建议是否有效且不伤质量。

## 二、我的成本分析主张（请逐项核实）

1. **迭代次数是主成本**：每轮整改平均经历"实施→审查→修复→复验"4–6 次模型运行（GLM 30–120 分钟/次、DeepSeek 15–45 分钟/次），而非一次通过。
2. **每次迭代带全量重建验证尾巴**：2,236 卡四 cohort 重建＋效果账本（41,665 行）＋选题链＋verify_full（17 项结构检查）＋独立目录逐字节复跑，每轮每次约 10–20 分钟。
3. **语义正确性机器查不了**：verify_full 17/17 只证明结构一致（哈希/引用/集合对账），证明不了"每条描述的效果解析是否正确"，因此每轮必须付一次独立语义审查。
4. **修复的实际改动量很小**：审查发现的多数问题修复后真实改动有限（例：一轮根因修复后全库 41,665 行状态变化为 0；另一轮为 641 行状态重登记），时间主要花在"证明现在对了"而不是"改错"上。
5. **审查发现的问题多为已知缺陷族复发**：规范化不对称、子串过匹配、层/命名空间混淆、归属门过严/过松、覆盖语义、上下文路由、签名/重建纪律等约 23 个陷阱族。
6. **真实案例**（可核对）：319 行 S2 误挂（同标签有效答案被判定"无兼容答案"）、HP 条件分支被空文本排除（4+4 行）、选题器首次读卡返回错误行（1,929 项语境错配）、同句机制抢占分类（605 项诊断）。
